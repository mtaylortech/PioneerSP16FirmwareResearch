# SP16 parallel-chat workflow audit — October 9, 2026

**Assessment: the four Ghidra analysts produced useful research, but the evidence does not establish that four analysts plus a separate integrator was the most efficient arrangement. Use one Ghidra analysis owner and one experimental owner as the default. Use an independent reviewer at consequential decisions; create extra analysts temporarily for demonstrably independent questions.**

This is an outside, adversarial assessment of the October 9 Send Amount round and the adjacent preparation/live cycle. It uses saved artifacts, chat prompts, turn timings, source inspection and independent original-ELF reads. It does not treat chat agreement, test counts, archive readiness or static byte matches as proof of instrument behavior. It is not a complete re-verification of the emulator, every historical experiment or the unfinished shared Ghidra integration. No firmware, helper or input was launched for this audit.

## Measured timing and its limits

The first analyst began at 7:19:54 p.m. America/Chicago; the last initial analyst response completed at 7:29:11 p.m. Initial durations were approximately 9.29 minutes for input, 7.78 for display, 5.05 for contract and 2.82 for the failed model turn. Their summed durations were about 24.94 minutes, overlapping within 9.29 minutes of wall time.

The initial integrator package completed at 7:41:03 p.m.: 21.15 minutes from the first analyst start, including approximately 11.87 minutes after the last initial analyst completed. Its own turn lasted approximately 20.31 minutes and included waiting, analysis, overlay implementation and controls. Integration was substantive engineering work; its entire duration must not be labeled administrative waste.

The four separately requested worker closeout reviews added about 17.16 summed chat-turn minutes, with overlap. Human-directed corrective/integration turns in the failed-model chat and subsequent shared-project integration add further work, excluded from that closeout sum. These figures are elapsed turn durations, not CPU utilization, billable tokens or human attention measurements. There was no matched single-chat run, so neither a net speedup nor a percentage saving is established. The observed overlap is real; the claim that five chats outperformed a simpler arrangement remains unproved.

## Problems and discrepancies

1. **A known contradiction failed to control the test handoff.** The [earlier Send Ghidra closeout] `2026-10-09-send-amount-ghidra-closeout.md` (evidence not published) already identified both the observer's identifier/name conflation and the absence of an experiment-ready positive drag route. The four analyst prompts explicitly included those warnings. Nevertheless, the experimental owner prepared the guest at 7:30:48 p.m. from the old fixture. At 382.803 seconds it failed the widget assertion before any Send gesture. This is a concrete failure of coordination between analysis and testing. Static evidence supports the contract defect, but the failed live assertion omitted actual operands; it does not conclusively identify which operand failed. [Live handoff] `../experiments/mixer-send-live-20261009-193048/HANDOFF.md` (evidence not published), [session clock] `../experiments/mixer-send-live-20261009-193048/session-clock.json` (evidence not published).

2. **Large test counts concealed an incorrect premise.** The earlier preparation reported 59 offline checks, yet its synthetic memory set the wrong name cell to the same value as the widget identifier. The fixture mirrored the incorrect observer assumption. The later contract controls separated the values and exposed the defect. Test count is a weak readiness measure when fixtures share implementation assumptions. The new distinct-value controls were useful; the round should receive credit for those, not credit for discovering a previously documented warning. [Historical fixture] `../experiments/mixer-send-preparation-20261009/identifier-contract-correction-20261009/before/offline_controls.py` (evidence not published), [discriminating controls] `../ghidra/parallel-send-round-20261009/contract/discriminating-controls.json` (evidence not published).

3. **Source ownership became distributed.** With explicit human authorization, the failed-model chat applied the correction to preparation while the separate integrator built a private corrected overlay and the experimental chat used its frozen old copy. This was authorized work, not an unauthorized mutation. Nevertheless, it created multiple integration locations and follow-up source-drift checks. Private snapshots preserved evidence, but did not ensure that the tested package reflected the latest accepted decision. [Patch provenance] `../experiments/parallel-send-integration-20261009/PATCH_PROVENANCE.md` (evidence not published), [live source distinction] `../experiments/mixer-send-live-20261009-193048/concurrent-source-readback.json` (evidence not published).

4. **The corrected preparation still has a stale launch receipt.** Independent readback found that prepared/lifecycle-validation.json retains observer SHA-256 6f573780378d40d11b994970e83c21b9173f3df15a8194ad21e9eaf0a66a9bcf, while the corrected source is 6c0d1b643874e734e336a1a1e6cee839ff3cbfa87bc2d01c5f0fd070af175aa0. The launcher explicitly checks these identities and should reject the current mismatch before a guest launch. Thus this is an unfinished packaging state, not proof that the launcher would silently accept unvalidated code. A passing historical receipt and 56 correction controls do not alone make the corrected preparation launch-ready. [Launcher] `../experiments/mixer-send-preparation-20261009/prepare_authorized_run.py` (evidence not published), [receipt] `../experiments/mixer-send-preparation-20261009/prepared/lifecycle-validation.json` (evidence not published).

5. **Common-source agreement was easy to overvalue.** The successful analysts reused much of the same earlier export set and were told the same existing conclusions. Independent original-byte rereads can corroborate those facts, but three matching reports do not provide three independent runtime confirmations or three distinct discoveries. Judge each chat by new coverage and its effect on the next decision.

6. **The current blocker needs runtime information.** Additional static descriptions cannot settle runtime-populated listener contents. Display and async research can support a later mutation test, but neither supplies the missing live input-route prerequisite. An all-four-finished barrier delays action when only a smaller dependency set is required. The integrator's owned-target inspection proposal corrects this ordering. It still leaves Desktop/global coverage incomplete and must not be promoted to proof of universal touch absence.

7. **Closure multiplied checkpoints.** Four reviews, individual handoffs/completion files, fixture integration, the offline integrator package, runtime review and a subsequent batch integration all touched related status. These tasks were explicitly requested and often preserved useful failures. The inefficiency is in the chosen recurring workflow: separate reviews and repeated byte checks can outgrow their incremental decision value. Archive readiness describes completion of a chat's obligations, not completion of Send research.

8. **Project registration is stale.** Both SP16 registrations refer to the nonexistent Code Projects directory; usable files are under Code_Projects. This audit and previous chats encountered process-creation failures from that mismatch. Correcting registration would remove recurrent friction. The project also has no Git repository; automatic Git-worktree isolation is therefore unavailable in its present state. This audit neither changed registration nor initialized Git.

Independent audit reads confirmed the original ELF identity 3d1392a61323e73ea4f2fddef8fe9e0142add7a6f6fab79ab0eb0d5396555464, five decisive pointer/literal cells and both identified BX LR motion words. Construction literals select 0xf6c700; the press-name literal selects 0xf6ab44. This corroborates the distinct roles and narrow no-op claims. It supplies no live BSS values, global listener coverage or actual edit evidence. Saved controls were inspected, not rerun; no full suite or headless analysis was launched.

## Recommended operating arrangement

| Arrangement | Judgment for SP16 |
| --- | --- |
| One chat does analysis, preparation and testing | Suitable for a small serial question. Lowest handoff cost, but mixes implementation and evaluation and leaves no independent challenge. |
| One Ghidra chat plus one experimental chat | Best default. Separate static reasoning from live interpretation while keeping one experiment/package owner. |
| Those two plus an adversarial reviewer | Useful at consequential decisions, failed experiments or milestone claims. Reviewer challenges readiness and inference; it need not run continuously. |
| Four Ghidra analysts plus an integrator | Useful as a temporary research burst when questions are independent and results can change near-term decisions. Not justified as the standing arrangement for the present shared runtime prerequisite. |

The Ghidra owner should own static questions and annotations, returning a short evidence-backed hypothesis, remaining unknown, discriminating observation and disproof. The experimental owner should own the current package, harness changes, validation binding, run and live frontier; integration becomes part of that role for ordinary two-chat work. Analysis proposals reach it as patches or frozen artifacts rather than competing edits to preparation. The reviewer should challenge the input premise, ownership, synthetic fixture independence and success criteria before a costly run or a strong progress claim.

Run analysis of an independent question while a validated guest is observing. A test that depends on unfinished analysis must wait for that specific dependency. Use one immutable package revision with its validation identities for each run; new findings produce the next revision. A consequential contradiction in the selected package must be reconciled before launch. If an already-running guest must stop under its existing fault/scope rules, preserve the consumed copy and partial evidence rather than hot-patching it.

For temporary extra analysts, first state which independent uncertainty each can resolve and which near-term decision will change. Reuse a shared frozen export baseline; give each a private output directory; consolidate only accepted incremental findings. Have the coordinator consume completed critical results when dependencies permit rather than wait for unrelated work. One batch assessment normally suffices; reserve separate closeout reviews for material private-project changes, significant failures or contradictions.

This recommendation aligns with official OpenAI guidance: [subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) favor independent, read-heavy tasks and warn about coordination costs for concurrent writes; [worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees) provide file isolation for Git projects. These product facts support the ownership approach; the SP16-specific recommendation is this audit's judgment.

Observe actual owned identity/listener targets after known MIXER entry, then decide whether to analyze a newly found touch target or investigate a supported alternative input route. The round was worthwhile for particular findings and a better test decision. Its complete five-chat structure has not earned a standing role: reduced coordination and better dependency ordering are more defensible improvements than simply adding or removing analysts by count.
