# Reader/cache replacement fixture — October 10, 2026

**Question:** after replacing a sample file, do one reader, shared readers and a changed path produce fresh decoded audio?

**Result:** original 1.50 ARM reader/cache instructions reproduce the stale same-path case. Releasing every holder removes that entry and permits fresh same-path decoding. This closes a cache behavior question; normalization itself is not implemented.

| Case | Old sample after first reader unload | Reopen decode | Audio returned |
|---|---|---|---|
| One reader, same path | Refcount 0; destroyed | One `/sample.wav` open | Replacement PCM |
| Two readers, same path | Refcount 1; retained | No decoder open | Old PCM; same shared object, refcount 2 |
| Two readers, uncached changed path | Refcount 1; retained | One `/fresh.wav` open | Replacement PCM; other reader retains old PCM |
| Follow-up: release both readers, same path | Refcounts 2 → 1 → 0; destroyed | One `/sample.wav` open | Replacement PCM in a new object |

Each successful load delivered result 0 through the original load task to a fixture listener; original unload tasks delivered the matching reader. Original player attachment stored the reloaded reader. The missing-file control delivered result 2 with no attached sample. Completion alone therefore does **not** imply fresh bytes: the shared same-path case completed successfully with stale audio.
