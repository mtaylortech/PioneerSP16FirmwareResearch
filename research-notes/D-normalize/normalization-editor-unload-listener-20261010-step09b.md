# Step 09b — editor unload listener and the missing completion barrier

October 10, 2026, America/Chicago. **Completed static tranche; stopped at the first decisive gap. Step 09 remains partial.**

Question: does the original editor `+0x100` unload listener connect legal admission to acknowledged release and prevention of reacquisition?

**Result:** the complete-object constructor binds editor `E+0x100` to table **`0x830508`**, whose unload slot `+0xc` is **`0x0b4460 → 0x0b4468`**. That callback subtracts `0x100`, branches, then executes **`bx lr`**. It records no completion/result, checks no reader identity and requests no reload. The neighboring **load** callback `0x0b4448 → 0x0b4450` stores result at `E+0x138` and sets `E+0x13c`; that byte is not an unload acknowledgment.

The original outcome path `0x0b7850`, when executing on its expected owner thread, clears `E+0x13d`, requests unload of `E+0x134` with listener `E+0x100`, clears loading byte `E+0x10c`, and dispatches the editor outcome (except result 12) **after the unload request returns**. There is no local wait for the unload listener or populated-reader query in this branch. It does not itself bind request return to release completion.

**Decisive gap:** no source-bound release-completion barrier connects the caller's outcome/close notification to actual `E+0x134` release. The listener is a no-op, while the concrete scheduling service invoked by `0x0bd48c` through virtual `+0x10` with argument **1** has an unbound completion/return contract. That argument must not be guessed to mean asynchronous admission, synchronous completion, priority or exclusion. A synchronous service could repair part of this edge; it has not been established. No legal no-reacquisition interval was demonstrated. Discovery stopped without tracing that next scheduler contract.
