### Corrections / confirmations to Step 08

- The inferred initial-position operation is now established as seek-to-zero, **without truncation**. Fixed dot-prefixed staging, ignored staging deletion and nonexclusive/nontruncating open remain confirmed. If a longer staging file survives deletion, successful rewind plus shorter output can leave an old tail; this is a static failure consequence under the stated condition, not an observed fault.
- Outer Result checking detects recorded write−1/fsync−1; it does **not** detect every positive short write. Thus unchecked tree-output results are a concrete incompleteness risk even with a successful outer Result check. Gzip wrapper/finalization remains a **distinct unresolved gap**; these file-stream bodies do not close it.
- Transfer count is input accounting. Copy can report true with lost output or zero-transfer/stat-failure conditions, before destructor; no final status/close check follows. Existing destination pre-delete, destructive fallback cleanup/source-deletion failure and ignored deletion returns remain as in Step 08.
- Synchronization exists: file fsync plus connected global sync. Replace neither with a universal no-sync claim nor a durable-commit claim. No checked per-transaction file-and-parent commit is established by this stock writer.
- Ordinary Save and resume serialization/copy outcomes remain separate and unaggregated. No new evidence repairs that hazard. These are conditional effects if those stock services are invoked, not automatic Keep dependencies.

**Separate verdicts:** local function success can occur; complete intended bytes are not established; durable file/directory commit is not established. The stock editor save rejects an existing output and the stock project/file replacement wrappers pre-delete or fall back destructively. **Neither is suitable unchanged as the selected-original Keep transaction.** Required capability: uniquely owned checked staging, complete output/header/content validation, supported attribute policy, checked sync/close, identity/quiescence revalidation, same-filesystem direct rename without pre-delete/copy fallback, checked parent synchronization and recovery-aware outcomes. Existing import availability and host probe are building blocks, not its firmware implementation.

## Proposed minimal Keep sequence

1. Capture selected original reference/tag, resolved file identity, format/geometry/attributes/adjunct identity, scene/track/editor lifetime and project musical state. Acquire legal stopped-playback and worker/scheduler exclusion; handle busy/refused work before mutation.
2. Scan and uniformly scale the whole recording into uniquely owned private staging. Keep all existing stock PCM/preview buffers immutable. Validate complete intended frames/header/metadata using the declared numerical oracle. **The owner's peak ceiling is still undecided.** Discard abandons private work and leaves the selected file/audio unchanged.
3. Before commit, identify and release all affected real reader/cache/display holders through legal services; await every unload acknowledgment and prevent reacquisition. Retain restoration/recovery evidence. Revalidate selected identity and supported alias policy.
4. Finalize and independently validate staging, preserve supported attributes, check file sync/close and required recovery/directory state. Direct same-filesystem rename over selected pathname is the commit boundary, with no old-file pre-delete or copy fallback; check parent sync. Report post-commit uncertainty as committed uncertainty, never as Discard/original unchanged.
5. Reload every intended holder at the same reference/path through a **model-preserving** route. Require fresh decoded PCM and readiness; refresh waveform/peaks and UI acknowledgment. If refresh fails after commit, preserve the truthful committed/error state and recovery inputs.
6. Leave `.dat`, path assignment and serialized project/resume state unchanged when the stated invariants hold. If a concrete required callback contradicts that assumption, revise the effect envelope and qualify only those additional changes. Close the function after its supported success acknowledgment; verify subsequent playback and ordinary reload/restart in the later authorized environment.

This is a capability sequence, not implemented source, a runnable candidate or authorization for a trial. No new device/runtime fixture or peak threshold was selected.
