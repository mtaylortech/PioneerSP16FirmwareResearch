# Reader completion and reopening trace — October 10, 2026

Question: after accepted sample assignment, does the original 1.50 player complete a reader reload, and does same-path replacement necessarily produce fresh audio?

Result: a static chain now connects assignment → player request → unload/load callbacks → player reader attachment. **Same-path reload is conditional on shared-cache ownership.** The load method first looks up a decoded sample by path. Releasing the selected reader deletes that sample only when its reference count reaches zero. If another holder retains it, a load can succeed through cache reuse without opening the replacement file. This is an original-code branch result, not an observed stale-audio failure. No guest or firmware ran.

## Consequence and remaining limits

| Condition at reload | Static route | Limit |
|---|---|---|
| Same key, selected holder was last | Release evicts/destroys; cache miss can open/decode current file | Scheduling, successful decode and final audible bytes not observed |
| Same key, another holder survives | Cache hit can return the old shared decoded sample | No inode/mtime/content freshness check appears on this hit path |
| Changed path | New key can miss and open/decode | An already-cached destination can also hit; aliases and mount resolution remain open |

Stock SAVE & REPLACE completion `0x28bac8` still closes the editor, performs reset work and invokes the setter. Three local reset helpers only clear their supplied state/array in the inspected bodies. Optional `0x60da54` removes hash-matched entries from a separate collection and destroys their data; its full owner/destructor effects are not bound here. These inspected calls do not establish an unconditional eviction of all shared sample holders. [Save completion exports] `exports/save-completion/` (evidence not published). The stock save worker's earlier existing-destination rejection remains in force: this trace does not claim stock save rewrites an already-existing selected file. Same-path replacement is relevant to the proposed custom Keep route.

No live task order, actual holder count, selected instance, file readback, cancellation/retry behavior, audio output, shared-track refresh or UI response was observed. Static success/listener delivery does not prove durable audio/project storage. Normalize → Keep/Discard remains unimplemented; this is no new original-UI milestone.
