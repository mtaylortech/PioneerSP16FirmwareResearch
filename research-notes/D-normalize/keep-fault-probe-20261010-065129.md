# Disposable Keep transaction fault probe — October 10, 2026

**Complete: all eight host cases pass independent artifact verification. No firmware ran and no application code or existing fixture changed.** This is a minimal Python transaction model, not a shipped-ARM implementation or physical-storage qualification. Scope: the owner's new 16-minute host-only probe; first clock 06:51:29 UTC, ceiling 07:07:29 UTC. Functional checks completed at 06:54:31 UTC; reporting completed within that ceiling.

Question: can verified private staging and direct rename distinguish failures before replacement from synchronization failure after replacement, while retaining recovery evidence?

The [prototype] `probe.py` (evidence not published) creates a checked original-byte backup and intent record, syncs those files and their directory, creates staging exclusively, loops until all bytes are written, validates exact bytes and WAV geometry, syncs/closes staging, revalidates the original identity, syncs the directory, renames staging over the original pathname, and checks directory sync afterward. It performs no target pre-delete, copy fallback or automatic rollback. The separately executed [verifier] `verify.py` (evidence not published) reopens all artifacts without importing the prototype.

| Case | Saved result | Selected file / retained evidence |
|---|---|---|
| Successful control | `COMMITTED_SYNC_OK` | Exact candidate; original backup and intent retained |
| Positive short writes | `COMMITTED_SYNC_OK` | Exact candidate after 43 writes: 42 × 13 bytes, then 10 |
| Unchecked one-call short-write negative control | `NOT_COMMITTED` | Original unchanged; validation rejects 13-byte staging |
| Positive short write, then injected write EIO | `NOT_COMMITTED` | Original unchanged; 13-byte staging retained |
| Injected rename EXDEV | `NOT_COMMITTED` | Original unchanged; full staging retained; no fallback |
| Injected staging-file fsync EIO | `NOT_COMMITTED` | Original unchanged; full staging retained |
| Injected pre-rename directory fsync EIO | `NOT_COMMITTED` | Original unchanged; full staging retained |
| Injected post-rename directory fsync EIO | `COMMITTED_DURABILITY_UNCERTAIN` | Exact candidate installed; original backup and intent retained |

All five failures before commit preserve original content, inode, size, mtime and mode. All eight cases retain a byte-identical original backup plus intent hashes/path names. Backup, intent and recovery-directory fsync calls succeeded before each injected fault. Evidence is readable after normal child exit; automatic restoration and survival of power loss were not tested. `COMMITTED_SYNC_OK` means this host accepted the checked sync calls, not proof against a power failure.

The held original descriptor continues to read **old bytes after successful rename**, while reopening the selected pathname reads the candidate. Cache/reader refresh therefore remains a separate integration obligation. Another explicit limitation: committed staging uses mode 0600, replacing the fixture's mode 0644 and changing its inode. File attribute preservation is **not** implemented or passed.

Fixtures are newly generated 556-byte stereo PCM WAVs (16-bit, 48kHz, 128 frames). The candidate doubles safe synthetic values solely to distinguish contents; no owner-selected normalization ceiling/oracle is inferred. Read-only synthetic seeds are preserved and hash-checked: original `83b016e43f27527cfa17c8b12473aecb8183381ec892cf82e713cf19b83e8886`; candidate `60b36154f124573c135c95ffa614e73a5a3bc253f7c1ffd3c522bdeb433b3350`. Existing original fixtures were never opened by the probe.

Limits: real normal-path open/write/fsync/rename calls ran on macOS 14.8.9 arm64 with Python 3.10.1; filesystem type was not independently identified. Faults were injected at Python operation boundaries. Short-write injection performs a real prefix write and returns its count to a caller that requested the full buffer; it does not force a kernel-origin short write. Rename/sync faults raise before that selected OS call. No disk-full, real media I/O fault, cross-device move, crash, power loss, concurrent writer, symlink/hardlink race, close failure, startup recovery or firmware wrapper was exercised. Recovery evidence is retained, but no durable committed receipt or recovery policy is implemented. The model assumes one writer in an isolated directory; its identity check does not close a concurrent check-to-rename race. Exact-byte fixture checks are not a production full-file validation/streaming design, and no resource envelope is measured.

**Decision / next step:** the host model supports rename-only commit with exact-write handling, validation, checked sync and three distinct outcomes. It does not make the mapped stock wrappers safe unchanged. Hand off the transaction requirements and these receipts to the next process. That process still needs a release-bound attachment/worker ownership boundary, file attributes and original-reader refresh, target storage correspondence, and crash/recovery policy before an integrated Keep implementation can be called safe. Further firmware, device, application implementation or runtime work is not authorized by this completed probe. Full consolidated findings are in [P05](../history/handoffs/05-FEATURE-BOUNDARY.md).
