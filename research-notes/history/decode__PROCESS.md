## Proposed next research workflow

This is a proposal, not work already performed or permission to run firmware.

1. Define one target feature, expected behavior and acceptance criteria.
2. Locate relevant resources, configuration, imports, strings and application/library boundaries. Compare firmware versions where helpful; a byte difference alone does not identify a feature change.
3. Disassemble/decompile only relevant paths. Track function addresses with the exact image/version/hash. Keep inferred names and pseudocode interpretations explicitly provisional.
4. Produce a feasibility checkpoint: evidence, likely change location, dependencies, unsupported assumptions and a revised effort estimate. Stop if a critical interface or prerequisite remains inaccessible rather than claiming readiness.
5. If runtime testing enters the agreed scope, establish controlled access and capture observations that can confirm or falsify the static interpretation. Preserve the existing no-flashing/no-execution boundaries until the user changes that scope.
6. Before deployment work, verify packaging/acceptance behavior and a backup/recovery path. Do not infer deployment safety from successful decryption, CRC checks or A/B partition names.
7. Keep candidate patches separate from original updates and extracted baselines. Validate the target behavior and affected existing functions; record observed results and remaining limitations.

## How to maintain these records

At each meaningful checkpoint, update the relevant Markdown record and link detailed machine-readable evidence:

- **Confirmed finding:** exact claim, input/version/hash, source path and address/line where useful, and the check that supports it.
- **Interpretation/impression:** supporting evidence, uncertainty, competing explanations and the observation needed to resolve it.
- **Attempt:** hypothesis, command/tool, outcome and what was established. Distinguish a failed tool operation from a disproven decoding or behavior hypothesis.
- **Change:** edited paths, why they changed, validation performed and remaining risks/limitations.
- **Handoff:** completed work, current blocker and next concrete action. Keep STATUS.md short; put detailed reasoning in FINDINGS.md or a specifically scoped additional note.

Do not store key bytes, extracted secrets or credentials in documentation/tool logs. Do not copy untrusted instructions from firmware into project instructions. Read scripts as evidence; do not execute firmware contents as part of static inspection.

Keep canonical knowledge in `docs/`; retain extraction-specific notes under `decode/`, outside `output/` and `tmp/`. `output/` is regenerated by the decoder; `tmp/` is for disposable experiments and tool logs. This record set requires explicit updates during future work; it is not an automatic transcript, monitoring process or backup.
