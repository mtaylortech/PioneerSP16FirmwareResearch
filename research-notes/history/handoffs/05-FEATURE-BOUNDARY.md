### Existing audio caller does not cure commit failure

The WAV-related rewrite route beginning `0x5e5428` provides a concrete caller, rather than merely an isolated library helper. It constructs the staging pair through `0x659b04` at `0x5e5704`, opens its staging output at `0x5e57f0`, creates a WAV writer through `0x5e52c8`, and checks reader-to-writer copy result from `0x5b10f4` at `0x5e5838`. Writer and reader are destroyed before the commit call `0x5e5870 → 0x64e224`. The common return path then calls staging cleanup `0x643d58` at `0x5e57b4`, including after failed commit. This is a metadata-related WAV rewrite candidate from its surrounding metadata operations, **not established normalization**.

That cleanup checks/removes staging path `+0`, retries deletion with 50ms sleeps, and releases the two path strings. It does not restore original target `+4`. A concrete conditional failure sequence is therefore: existing target removed → rename fails → copy fallback fails → commit reports false → caller attempts deletion of remaining staging output. **The original path can already be lost when false is returned, and the new output is not necessarily retained for recovery.** This is static control flow, not observed file loss or a reproduced fault.

Generic replacement callers `0x6591ec/0x6592e0/0x659a30` likewise close output, test staging existence, invoke `0x64dd90`, then clean the staging pair via `0x644584`; no original restoration is established there. In the data caller, write return at `0x6592b0` is not checked before this progression. Application-level FileTools move callers inspected at `0x32f224/0x32f23c/0x32f3c0/0x3399c8` pass sync flag 0. Their surrounding data/resume workflows are not proved as a reusable selected-sample recovery transaction; no new project-wide recovery claim is made.

**Additional write limitation:** buffered flush `0x64ec68` calls `write` at `0x64ecac`, tests only return `-1` at `0x64ecb0`, then clears buffered count at `0x64ecc0`. A nonnegative short write is not checked against the requested count or retried in that branch. Stream destructor `0x64d8d8–0x64d8ec` has the same pattern. Thus even checking stored error plus later `fsync` is insufficient proof that all buffered sample bytes were written. No short-write fault was injected. Complete staging validation or exact-write handling is still needed before Keep.

### Conditional route and next discriminator

The credible route is **verified private staging → checked final output synchronization → direct rename to the original selected pathname → checked parent sync → original-path reload/cache refresh**. This is a behavioral requirement and candidate route, not an implemented design or selected hook. Rename should be the commit boundary; an error must not enter the stock delete/copy fallback. A directory-sync failure after successful rename means the path has already changed: it cannot be reported as an unchanged original or treated as Discard. Backup retention/recovery and a distinct committed-but-durability-uncertain result still need evidence.

Before reuse, resolve exclusive staging ownership, complete-frame/header/content checks, same-filesystem placement on actual storage, original identity/quiescence across commit, symlink/hardlink/open-reader effects, file attributes and metadata policy, and post-commit reader/cache refresh.
